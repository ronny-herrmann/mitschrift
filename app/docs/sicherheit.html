Unterlage für die IT-Sicherheit: Aufbau, Schutzmaßnahmen je Ebene, Angriffsfläche, ehrliche Stärken und Schwächen sowie die Maßnahmen bis zum Regelbetrieb. Stand: Testphase.

Architektur in Kürze

  • Ein Linux-Server (Ubuntu 24.04 LTS) bei Hetzner, Rechenzentrum Nürnberg. Alle Dienste laufen in Docker-Containern.
  • Einziger Eingang: Caddy als Reverse-Proxy auf Port 443 (Port 80 nur für die Weiterleitung auf HTTPS und die Zertifikatsausstellung).
  • Dahinter zwei getrennte Instanzen der Anwendung (Test und Produktiv) mit eigenen Daten, dazu das Sprachmodell (llama.cpp) – beide ohne eigenen Port nach außen, nur im internen Docker-Netz erreichbar.
  • Code kommt aus einem öffentlichen GitHub-Repository; der Server holt Änderungen selbst ab (Pull). Es gibt keine eingehende Verbindung für Auslieferungen.
  • Keine externen KI-Dienste, keine Cloud-APIs, keine Tracking- oder Analysedienste, keine Schriften oder Skripte von fremden Servern.

Angriffsfläche

  • Von außen erreichbar: HTTPS-Webanwendung (Anmeldeseite, nach Anmeldung die Schnittstellen und die Live-Verbindung), Port 80 (nur Weiterleitung), SSH.
  • Ohne Anmeldung erreichbar: Anmeldeseite, Oberflächen-Dateien (HTML/CSS/JS, keine Daten), /healthz (liefert nur {"ok": true}).
  • Ausgehend: Ubuntu- und Docker-Updates, GitHub (Code), einmalig Modell-Downloads (GitHub, Hugging Face), Let's Encrypt. Keine Nutzerdaten.
  • Lieferkette: Python-Pakete (PyPI), Docker-Images (Docker Hub, GitHub Container Registry), Modell-Dateien.

Stärken

Was gut ist

  • Geschlossenes System: kein Datenabfluss an externe KI oder Cloud-Dienste – das größte Risiko typischer KI-Lösungen entfällt.
  • Kleine Angriffsfläche: ein Eingang, alles andere intern.
  • Pull statt Push: kein Deploy-Schlüssel auf GitHub, kein offener Admin-Zugang für die Auslieferung.
  • Quelloffen und nachvollziehbar: jede Änderung ist mit Datum und Inhalt im Repository dokumentiert.
  • Arbeitsplatz-PCs brauchen keine Software und keine Sonderrechte – nur einen Browser.
  • Reproduzierbar: Server lässt sich per Skript in ca. 15 Minuten neu aufbauen.

Schwächen (ehrlich)

  • Ein gemeinsames Passwort statt persönlicher Konten; keine Rollen, alle Angemeldeten sehen alle Aufnahmen.
  • Kein Audit-Log (wer hat was geöffnet/gelöscht).
  • Daten auf der Festplatte nicht zusätzlich verschlüsselt; Sicherung liegt auf demselben Server.
  • SSH ist offen und derzeit mit Root-Passwort (per E-Mail von Hetzner) statt Schlüssel.
  • Docker-Images und Modelle über „gleitende“ Versionen/ohne Prüfsumme geladen; Python-Abhängigkeiten nicht fest gepinnt.
  • Kein Monitoring/Alarmierung; ein Server = ein Ausfallpunkt.
  • Wer Schreibrechte am GitHub-Repository hat, kann Code auf den Server bringen (Test sofort, Produktiv über den Freigabe-Branch).
  • Adresse über den Dienst sslip.io (Test) statt einer städtischen Domain.

Wiederanlauf

  1. Neuen Server mit dem Einrichtungsskript anlegen (ca. 15 Minuten, vollautomatisch).
  2. Letzte Datenbanksicherung zurückspielen.
  3. Adresse (DNS) auf den neuen Server zeigen lassen.

Audio wird bewusst nicht gesichert; nach einem Totalausfall sind Texte und Protokolle bis zur letzten Sicherung vorhanden, Audio nicht.

Fragen, die die IT-Sicherheit stellen wird – und die Antworten

Welche Daten verlassen den Server?

Keine Nutzerdaten. Ausgehend gibt es nur Software- und Code-Updates und einmalige Modell-Downloads.

Wer hat Administrationszugang?

Derzeit das KI-Management (Hetzner-Konto, GitHub-Konto). Für den Regelbetrieb: benannte Administratoren mit persönlichen Schlüsseln und Vertretungsregelung.

Wie werden Sicherheitslücken geschlossen?

Betriebssystem automatisch; Anwendung und Abhängigkeiten per Änderung im Repository, die der Server innerhalb von Minuten übernimmt. Schwachstellen-Scans sind als Maßnahme geplant.

Ist der Code geprüft?

Automatische Tests laufen bei jeder Änderung. Eine unabhängige Prüfung (Code-Review, Penetrationstest) ist vor dem Regelbetrieb sinnvoll; der Code ist dafür vollständig offen.

Warum ist das Repository öffentlich?

Es enthält nur Code und Dokumentation, keine Daten, Passwörter oder Schlüssel. Offenheit erleichtert Prüfung und Nachnutzung durch andere Kommunen. Sicherheit beruht nicht auf Geheimhaltung des Codes. Auf Wunsch kann es privat geschaltet werden (der Server braucht dann einen Lese-Schlüssel).

Kann das auch im eigenen Rechenzentrum laufen?

Ja. Voraussetzung: ein Linux-Server mit Docker (für den Regelbetrieb mit GPU). Das Einrichtungsskript ist dasselbe.

Was passiert bei einem Fehler in einer neuen Version?

Sie landet zuerst nur in der Test-Instanz. Produktiv wird erst nach Freigabe aktualisiert; Zurückrollen ist eine einzelne Aktion im Repository.
